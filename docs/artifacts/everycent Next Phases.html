7e

Credit lifecycle

Recommended first

This is the one place the plan's money is wrong today. A card with a positive balance should count as cash, but everycent treats an overpayment as cash overspending and never adds the positive balance back, so the plan loses that money. Closing a positive card takes its balance out twice.

Includes

  • Positive card balances: the part above zero counts in Ready to Assign; spending while positive is cash until the card owes again
  • Close and reopen with positive, zero and negative balances; the payment category stays visible on close (YNAB does)
  • The close dialog's two wordings (positive balance vs debt)
  • Card payment targets on positive cards (skipped in 8e)
  • Parity pass of every Phase 7 credit case in both themes

Depends on

  • 7a–7d; 8e payment targets

Confirmed already

  • YNAB counts a card's balance above zero as cash in Ready to Assign deferred.md
  • Closing a card leaves its payment category visible deferred.md
  • YNAB can't change an account's type; everycent keeps changes within a family

To check in YNAB

  • Where leftover payment money goes when a card closes; the exact dialogs verify.md
  • Line of credit readings that looked unreliable in the API verify.md

Reconciliation

Small phase

Four README items, and it clears a run of Phase 5 deferrals: reconciled rows show a lock that can't be opened, and transfers and splits with a reconciled side are refused with TRANSFER_RECONCILED where YNAB would offer to unlock them.

Includes

  • Reconcile flow: confirm the cleared balance, or enter the bank's balance
  • Automatic balance adjustment transaction for a difference
  • Lock reconciled transactions, with YNAB's warning before editing one
  • “Unlock?” for a transfer or split whose other side is reconciled (register, bulk edit)
  • Last reconciled date per account

Depends on

  • Phase 5 register (cleared toggle, lock icon, transfers, splits, bulk edit)

To check in YNAB

  • The reconcile dialog's steps and copy; the adjustment's payee and category
  • What the edit warning allows (unlock one row, or the whole reconciliation?)
  • Bulk Move or Delete with a reconciled transfer side: skip, unlock or refuse verify.md
  • Reconciling a credit card or a tracking account

Scheduled transactions

Large phase, part 1

Future-dated transactions are plain transactions today; YNAB keeps them as scheduled ones. This stage gives them their own model and the register's upcoming list, without touching the plan yet.

Includes

  • Repeat frequencies: once, daily, weekly, every other week, twice a month, every 4 weeks, monthly, every other month, every 3 or 4 months, twice a year, yearly, every other year
  • Upcoming transactions in the register: enter now, skip, edit
  • Scheduled splits and transfers
  • Existing future-dated transactions become scheduled ones

Depends on

Ground rules

  • Match YNAB one to one; check, don't assume. Settle each stage's questions in the test plan through the API and the web app before building; what can't be settled goes to docs/verify.md, not into code as a guess.
  • Money stays exact. Card balances crossing zero, adjustment transactions and loan interest are bigint minor units with a currency; no step creates or destroys money in the plan.
  • Build one vertical stage at a time. Engine rule → PostgreSQL integration test → API schema → generated client → UI → browser check in both themes. Run pnpm check before marking a stage done.
  • Keep the docs current. Each stage updates the README checkboxes, docs/deferred.md, docs/verify.md and this page.
